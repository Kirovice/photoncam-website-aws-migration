## 范围表的作用 / 範囲表の役割

范围表回答：本项目负责做哪些事，做到什么程度，哪些后续处理。范围不清楚，容易把网站迁移、域名切换、数据库迁移和 App 改造混为一项任务，造成费用、工作量与验收预期不一致。

範囲表は、何をどこまで実施し、何を後続で扱うかを定義する。Web 移行、ドメイン切替、DB 移行、App 改修を混同すると、費用・作業量・受入の認識がずれる。

| 字段 / 項目 | 作用及为什么要写 / 役割・記載理由 |
|---|---|
| 编号 / ID | 稳定引用范围条目，方便评审和变更追踪。レビュー・変更時に同じ項目を参照する。 |
| 范围分类 / 範囲区分 | 区分当前、后续、扩展和排除项，避免把全部长期目标当作当前交付。現在・後続・拡張・対象外を区別する。 |
| 内容 / 内容 | 明确实际工作对象，避免只写含义宽泛的“迁移”。具体的な作業対象を明示する。 |
| 依据 / 根拠 | 指向用户约定或调查事实，说明为何纳入。利用者合意・調査事実へ追跡できるようにする。 |
| 边界与条件 / 境界・条件 | 说明前置条件和影响边界。着手条件と影響範囲を示す。 |
| 认定状态 / 状態 | 区分已约定、范围解释和待确认；不代替实现状态。合意・解釈・未決を区別し、実装状態と混同しない。 |

用词说明：“本轮纳入”在范围表中指当前 dev 工作范围；“第一轮控制台、第二轮 CloudFormation”是练习轮次。两种用法容易混淆，阅读时要区分。更清晰的说法是“当前 dev 阶段”。本次讲解文档不据此修改 SC01、SC02 的 Excel 原文。

用語：範囲表の「本轮」は現在の dev 作業範囲を指し、Console 第1回・CloudFormation 第2回とは異なる。説明上は「現在の dev 段階」と読む。本書作成だけで SC01・SC02 の Excel 文言は変更しない。

这一条把从源码到可访问网站的三个部分纳入当前 dev 范围。

### 为什么一起写 / 一緒に記載する理由

源码能编译但没有环境，无法验证部署；资源已创建但网站打不开，也不能算完成；旧 ZIP 能上传但源码无法重建，以后修改网站就难以可靠发布。因此要覆盖完整过程。自动重复执行这些步骤由 SC02 另行规定。

ビルドだけでは配備を検証できず、資源作成だけではサイト利用を保証できない。古い ZIP の配信だけでも、今後の変更を再構築できるとは限らない。このため一連の結果を対象とする。自動実行は SC02 で定義する。

### 为什么先验证构建 / ビルド検証を先に行う理由

2026-09-15 的调查发现：依赖清单为 Docusaurus 3.6.3 系列，锁文件为 3.0.1，线上与 ZIP 标记为 3.5.2。构建命令和预期输出已查到，但实际重建尚未验证。需要先确认依赖、构建环境和输出，才能设计 AWS 构建与发布方案。这属于设计前的技术调查，不等于提前创建 AWS 资源。

調査では依存指定3.6.3系、ロック3.0.1、公開物3.5.2が不一致。コマンドと出力先は確認したが再ビルドは未検証。依存・環境・生成物を把握して AWS 方式を設計する。これは設計前の調査であり、AWS 資源の先行構築ではない。

## SC02：GitHub 与 CodePipeline 自动构建部署

### 作用与示例 / 役割と例

修改源码后，按约定自动完成构建，并将检查成功的产物发布到 AWS dev。预期顺序是：提交源码、触发流水线、安装依赖并构建、检查产物、发布 dev。

ソース変更後、合意した条件でビルドし、検査に成功した成果物を dev へ自動配備する。コミット、起動、依存導入・ビルド、検査、配備の順を想定する。

例如，修改首页文字并提交到约定分支后，系统构建新版网站，检查成功后让 dev 显示新文字。具体检查内容还需要设计。

例：トップページの文言を対象ブランチへコミットすると、新版をビルド・検査し、dev に反映する。検査の詳細は後続設計で決める。

### 与 SC01 的区别 / SC01 との違い

SC01 要求能够构建、部署和访问；SC02 要求将这些步骤组织成可自动重复执行的流程。手工部署成功一次，只证明方法可行，不能证明自动部署已完成。

SC01 はビルド・配備・アクセスの実現、SC02 はその自動反復を要求する。手動で一度成功しても、自動配備の完了証明にはならない。

### 为什么选这些名称与依据 / 名称と根拠

GitHub 管理源码，CodePipeline 衔接各阶段，这是用户已提出的方向。CodePipeline 组织流程，真正的编译还需要构建执行环境。前面提出的 CodeBuild 是实现候选，其详细配置属于设计。

GitHub はソース管理、CodePipeline は工程連携という利用者の方針。実際のコンパイルには実行環境が必要で、CodeBuild はその候補。詳細設定は設計事項。

| 依据 / 根拠 | 内容 / 内容 |
|---|---|
| S01 | 项目规则要求 GitHub 与 CodePipeline 联动自动部署。規則で GitHub・CodePipeline 連携を要求。 |
| S06 | 用户要求以后把编译步骤也迁入 AWS。利用者がビルド工程の AWS 移行を要求。 |

二者一起说明自动化包括源码构建，不只上传已生成 ZIP。

両者により、ZIP 転送だけでなくソースビルドも自動化対象であることを示す。

### 为什么关联 Q05 / Q05 を関連付ける理由

自动化方向已约定，触发与发布规则仍未确定：哪个分支触发，成功后是否直接发布 dev，失败如何停止和通知。它们影响权限和流水线设计，所以记录为 Q05，不擅自认定所有分支的每次提交都应发布。

対象ブランチ、成功後の自動公開、失敗停止・通知は未決。権限とパイプライン設計に影響するため Q05 で管理し、全ブランチの全コミットを公開するとは決めない。

## SC03：整个网站的正式迁移与运维交接

### 作用与实施顺序 / 役割と実施順

项目最终需要把网站迁到 AWS，并使环境能够持续维护。“后续纳入”表示属于整个项目，但在 dev 验证之后实施。dev 使用测试地址；正式迁移让真实用户通过约定正式地址访问 AWS 上的网站，并确认页面、图片和链接正常。

最終的に AWS へ移行し、継続保守可能にする。「後続対象」は dev 検証後の実施を意味する。本番移行では合意した正式URLで実利用者がアクセスし、ページ・画像・リンクを確認する。

是否改域名、修改哪部分域名配置尚未确定，需要结合域名边界处理。

ドメイン変更の有無・設定変更範囲は未確定で、ドメイン境界の確認が必要。

### 为什么先 dev 验收 / dev 受入を先行する理由

正式切换会影响真实用户。先证明源码可构建、网站可部署、页面和资源及深层链接正常、自动部署符合约定、失败有经过验证的恢复方式。这些结果形成正式迁移方案的输入。只看首页可以打开不足以决定切换。

本番切替は利用者に影響するため、ビルド・配備、ページ・資産・深いURL、自動配備、復旧を先に検証する。その結果が移行計画の入力となり、トップページ表示だけで判断しない。

### 运维交接为什么包含在范围内 / 運用引継ぎを含める理由

| 交接内容 / 引継ぎ項目 | 用途 / 用途 |
|---|---|
| 日常发布 / 通常配備 | 后续修改时能够更新。変更を正しく反映する。 |
| 故障检查与通知 / 障害確認・通知 | 异常能够被发现和处理。異常を検知して対応する。 |
| 回退与恢复 / 戻し・復旧 | 新版出问题时恢复。問題発生時に復旧する。 |
| 费用检查 / 費用確認 | 持续掌握支出。継続的に支出を把握する。 |
| 责任与操作资料 / 責任・手順 | 明确谁负责、怎样执行。担当と実行方法を明確にする。 |

即使由用户自己维护，也需资料供以后查阅，避免上线后无人掌握运维方法。

利用者自身が保守する場合も、時間が経ってから再実行できる資料が必要。

### 依据与条件 / 根拠・条件

S01 包含 dev 后正式迁移和运维交接。“完成 dev 验收与正式迁移评审后”是两道判断：dev 验收证明方案可行；迁移评审确认切换范围、时间、操作、回退条件和责任。已约定的是最终交付范围，不代表已具备切换条件或已定日期。

S01 に基づく。dev 受入は方式の実証、移行レビューは範囲・時間・手順・戻し条件・責任の確認。合意済みなのは対象範囲であり、切替可能状態や日付ではない。

## SC04：CloudFormation 第二轮重建与复测

### 作用 / 役割

第一轮通过 AWS 控制台构建并验证后，保存资料和必要数据，核对并清理专用资源，再用 CloudFormation 重建和测试。依据是 S01 的学习顺序。

第1回 Console 構築・検証後、資料・必要データを保存し、専用資源を確認・削除して CloudFormation で再構築・再試験する。S01 の学習順序に基づく。

CloudFormation 将资源配置写成模板，由 AWS 根据模板创建环境。模板便于版本管理、重复创建和比较配置变化。这里重建的是 AWS 环境，不等于网站源码编译；若模板创建构建流程，该流程之后才执行编译。

CloudFormation はテンプレートで資源構成を定義し、環境を作成する。版管理・再作成・差分確認に利用する。環境再構築と Web ソースビルドは別工程である。

### 为什么先控制台后模板 / Console を先行する理由

先通过实际操作理解参数与效果，再学习如何用模板表达同样的设置。例如先设置并验证访问权限，再理解模板中对应的配置，遇到差异时更容易排查。

実操作で設定と効果を理解してからテンプレート表現を学ぶ。例えばアクセス権を検証した経験により、対応するテンプレート設定や差分の原因を理解しやすくする。

### 为什么保存后清理 / 保存後に削除する理由

1. 保存配置、测试证据和必要数据，便于清理后追溯与比较。設定・試験証拠・必要データを保存する。
2. 区分需要保留、共享和可以删除的资源。保持・共有・削除可能な資源を分類する。
3. 清理第一轮专用资源，控制费用并准备重建。第1回専用資源を削除し費用を管理する。
4. 用模板重建，验证模板能够创建所需环境。テンプレートで必要環境を再作成する。
5. 复测，确认新环境满足同样业务要求。再試験で同じ業務要件を確認する。

“专用”不能扩大为共享或生产资源；执行前必须确定具体清理清单。

「専用」に共有資源や本番資源を含めず、実行前に削除一覧を確認する。

### 为什么还要复测 / 再試験する理由

资源创建成功不等于网站功能正常。仍需验证页面、资源、深层链接及该轮包含的构建部署流程。两轮尽量共用业务验收标准，保存各轮实绩以比较是否实现同样结果。

資源作成成功はサイト正常動作の証明ではない。ページ・資産・深いURL・対象ビルド配備を再検証し、業務受入条件を共用して各回の結果を比較する。

本条交付包括可重建环境的模板、重建记录和复测证据；目前确认的是范围，尚未实施。

成果は再構築用テンプレート、構築記録、再試験証拠。現時点は範囲合意であり未実施。

## SC05：容器、Kubernetes 学习与可行性

### 作用与区别 / 役割と違い

分类为扩展评估，前两轮之后评估是否开展。S01 要求先学容器，再学 Kubernetes，并先说明架构变化、费用及清理。

追加評価として、前2回の後に実施可否を判断する。S01 に従いコンテナ、Kubernetes の順で学び、構成変化・費用・削除方法を先に説明する。

| 对象 / 対象 | 含义及本项目可能用途 / 意味・利用例 |
|---|---|
| 容器 / コンテナ | 打包程序及运行依赖。例如将静态文件和 Web 服务打包运行。プログラムと実行依存をまとめ、静的資産と配信用サービスを実行する例。 |
| Kubernetes | 管理容器的部署、数量、更新和故障后的重新启动。コンテナの配備・数・更新・障害後の再起動を管理。 |

这些是可能的练习方式，不是已经确定的生产架构。

これらは演習例であり、確定した本番構成ではない。

### 为什么不写第三轮必做 / 必須実施としない理由

当前已知发布物为静态文件。容器引入镜像构建、存放、运行和更新工作；Kubernetes 进一步引入集群和编排管理。它们有学习价值，但是否值得实施，需衡量收益、成本与维护负担。先评估，再决定实施与深度，不因学习意愿直接认定正式网站需要它们。

現在の配布物は静的ファイル。コンテナではイメージ作成・保管・実行・更新、Kubernetes ではクラスタ・編成管理が加わる。学習価値と費用・保守負担を評価し、実施範囲を決める。

### 实施前需要说明什么 / 実施前の説明

- 架构变化：应用由什么运行、访问经过什么、构建部署如何改变。構成：実行方式・アクセス経路・配備変更。
- 费用：增加什么计费资源、运行多久。費用：追加資源と利用期間。
- 清理：如何删除练习资源、保留什么证据。削除：資源の撤去方法と証拠保存。

控制台与 CloudFormation 回答“怎样管理资源”；容器与 Kubernetes 回答“怎样运行和管理应用”。两类可以组合，不能当作互斥选项。即使最终不采用 Kubernetes，前两轮练习仍然有效。

Console・CloudFormation は資源管理、コンテナ・Kubernetes はアプリ実行管理。組み合わせ可能で、排他的選択肢ではない。Kubernetes 不採用でも前2回の成果は有効。

当初は App 開発・ストア公開・機能改修を一括対象外としていた。利用者の将来拡張希望により、Web 機能改修の一律除外を取り消した。

当前有效表述：**当前以网站迁移为主，保留后续功能扩展条件；新增功能经过影响分析后纳入。** App 开发和 App Store 发布仍不在范围内。依据为 S01 和 2026-09-17 用户补充约定。

現在の有効な方針：**Web 移行を中心とし、将来の機能追加に備える。追加機能は影響評価後に取り込む。** App 開発・ストア公開は引き続き対象外。S01 と本日の追加合意が根拠。

### 为什么仍需区分网站和 App / Web と App を区別する理由

网站介绍拍照、滤镜、照片编辑，但这些产品功能属于 App。迁移介绍这些功能的网站，不等于开发 App。项目名称相同不代表网站、App 和相关服务属于同一交付范围。

サイトが紹介する撮影・フィルター・編集機能は App の機能。紹介サイト移行は App 開発を意味せず、名称が同じでも成果範囲は同一ではない。

| 工作 / 作業 | 当前处理方式 / 現在の扱い |
|---|---|
| 迁移网站页面、图片、教程 / Web 資産移行 | 属于迁移范围。移行対象。 |
| 修复迁移引起的路径错误 / 移行に伴うパス修正 | 属于必要适配。必要な移行対応。 |
| 调整 AWS 构建所需配置 / AWS ビルド設定 | 属于既定构建迁移。合意済みビルド移行。 |
| 新增网站页面或功能 / Web 機能追加 | 可以提出并在影响分析后纳入，不预先整体排除。影響評価後に対象化可能。 |
| App 新增滤镜 / App フィルター追加 | 不属于网站迁移。Web 移行対象外。 |
| App Store 发布 / ストア公開 | 不属于当前范围。現在の対象外。 |

### “提前预留”具体是什么 / 拡張への備え

1. **源码可维护**：保留依赖、构建说明和版本记录，使以后能够继续开发。ソース・依存・ビルド説明・版記録を維持し、継続開発を可能にする。
2. **发布流程可扩展**：新增页面和修改功能后，能通过构建部署流程发布。追加ページ・変更機能をビルド配備できるようにする。
3. **设计说明扩展边界**：若以后新增登录、表单或后台服务，说明哪些部分需要增加或调整。ログイン・フォーム・バックエンド追加時に必要な変更箇所を基本設計で説明する。

登录、表单、后台只是解释扩展影响的例子，并非本次已经要求实施的功能。

ログイン等は拡張影響の例であり、今回の実装要求として確定していない。

需求明确后，再评估架构、费用、安全及测试影响，更新相关要件与设计。现在不为用途未定的功能先建数据库、后台或 Kubernetes，也不承诺所有未来功能都无需改造即可加入。

具体化後に構成・費用・セキュリティ・試験の影響を評価し、要件・設計を更新する。未定機能のための資源は先行構築せず、無改修であらゆる機能を追加できるとも約束しない。

### 为什么保留变更评估 / 変更評価を残す理由

弹性意味着可以根据需求修正范围，同时明确新增工作带来的影响。它不等于事先承诺无限制的功能开发。瀑布流程允许返回前序阶段修订，要件、设计和测试资料需要一起更新。

柔軟性とは要求に応じて範囲を変更し、追加影響を明示すること。無制限な開発の事前約束ではない。ウォーターフォールでも前工程へ戻り、要件・設計・試験を整合させる。
